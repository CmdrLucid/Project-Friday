# Sound: getting independent of the emulator (plan, 2026-10-28)

User goal (2026-10-28): 'sound' = after the picture (stage 2, done), also the sound should not depend on the GPGX emulator.  Facts measured today, then the options.

## 1. What the sound side is today
- 68K -> Z80 interface is tiny: command byte at Z80 RAM `$1FFF`, arguments `$1FFC` / `$1FFD`, bank register, bus request (FORMATS 'Sound driver').  In the two recordings `20261012_2106` (6000 frames) and `20261016_0039` (4730 frames) the 68K wrote 174 / 64 mailbox bytes (170 / 59 commands, 15 / 14 distinct ids).
- The Z80 runs the game's sound driver (disassembly `~/landstalker_disasm/code/audio/sounddrv.asm`, music / sfx data in the ROM, streams read through the banked window `$8000`) and writes the chips: YM2612 (FM + one DAC channel) and the SN76489 (PSG).
- GPGX emulates: Z80 CPU, Z80 bus / banking, YM2612, PSG, the mixer; the 68K side is already native.

## 2. Golden trace (built today: `tools/patch_sndtrace.py`, `tools/sndtrace.py`, env `LANDSTALKER_SNDTRACE=file`)
One text line per YM2612 write (`Y frame who cycles port value`), PSG write (`P`), 68K mailbox write (`M`), count of driver upload writes (`U`).  Measured:
- the trace is DETERMINISTIC: two runs of the same recording give byte identical files (1.28 M lines in 6000 frames of the intro recording).
- 90 % (intro) / 74 % (Mercator walk) of all YM2612 data writes are the DAC register `$2A` = the drum samples streamed one byte at a time by the Z80; the rest is about 4000 writes per FM register over the run (note changes, key on / off, instrument loads), plus 26 381 PSG writes in the intro (speech blips, noise effects).
- all YM writes come from the Z80 (the 68K never touches the chips directly).

## 3. Options
A. **Native port of the Z80 driver (recommended).**  Port `sounddrv.asm` (the driver is a few hundred lines of Z80 code plus data tables) to C: a function `snd_command(id, arg)` called by the 68K side's mailbox write and `snd_tick()` once per driver tick (the driver runs on the Z80's VBlank / timer interrupt), writing the YM2612 and PSG through a small chip interface.  Keep the chip models (YM2612 core, SN76489 core) as libraries: they are the hardware, not the system emulator.  Verification by differential test: run the Z80 emulation and the port side by side on the same commands and compare the register write sequence with the golden trace (same method that found the 68K translation bugs).  What it gives: no Z80 CPU emulation, the sound clock is ours (music at normal speed during fast forward = GitHub issue #11 part 2, no catch-up speed at alt+tab, easy music replacement for modding).  Cost: the DAC sample streaming (90 % of the writes) has to be modelled as PCM mixed directly instead of byte writes with Z80 timing; the exact cycle timing of every write is not needed for FM / PSG notes, but the DAC pitch must be exact.
B. **High level music engine** (own sequencer, own synthesis or sampled instruments): freedom for HD sound, but no longer the cartridge's sound; needs the music format fully understood and a lot of listening checks.
C. **Keep GPGX for sound** and only decouple its clock (run it on its own thread at normal speed): smallest step, solves issue #11 part 2 but not the emulator question.

## 4. Decision 2026-10-28: A, as a RECOMPILER (not a hand port)
User chose A.  Refinement found the same day: a hand written C port of the driver would be game code in the repository (rule: never commit game code, not even snippets).  So the Z80 driver is handled like the 68K code: a tool in the repo (`tools/z80recomp.py`, built on `tools/z80dis.py`) generates C from the user's own ROM at build time; the generated C is never committed.  Facts measured:
- the driver is the 8 064 byte image `SoundDriver` at ROM `$1F6000` (US ROM; code `$0000..$10A2`, data tables behind it); the 68K copies `$1F81` bytes into Z80 RAM at start (`InitZ80Driver $0006FA`).  The driver is the Cube / Idaware sound driver (same family as Shining Force II).
- `tools/z80dis.py` decodes it: 2 177 reachable instructions (the lordmir disassembly lists 2 180; the call / jr / jp / djnz / ret counts match exactly), 36 distinct mnemonics, no indirect jumps (`jp (hl)`), no interrupts (the main loop polls YM2612 timer B bit 1 for its tick), one `ldir`-free instruction mix: ld, jr, inc, call, add, jp, or, cp, push, pop, xor, ret, and, bit, djnz, rra, sbc, exx, srl ... small.
- self modifying code: the driver patches the immediate of a few `ld b, n` instructions (Z80 `$751`, `$75A`, `$9AB`, `$9B4` = the YM register select of the vibrato / frequency write, and `Dac_Loop+1` = the DAC delay), seen as the only differences between the ROM image and Z80 RAM after start (51 bytes in total, the rest are the channel variables at `$1300..`).  The recompiler reads those immediates from the memory image.
- the DAC (74 - 90 % of the chip writes) is paced by instruction counts in the main loop (`Dac_Loop`): the recompiled code must carry exact cycle counts (the decoder returns them), because the DAC pitch depends on them.
- timer: the tick comes from YM2612 timer B (value `YM_TIMER_VALUE`); the chip model has to provide the timer flag.

## 5. Steps
1. (done) golden trace + summary tool.
2. (done) the driver image found, SMC sites, instruction census, flow decoder `z80dis.py` (agrees with the lordmir listing).
3. Semantics: `z80recomp.py` emits C for every reachable instruction (registers, flags, cycle counter, memory map: Z80 RAM 8 KB mirrored, YM2612 `$4000..$5FFF`, bank register `$6000`, PSG `$7F11` through the 68K bus, banked ROM `$8000..`).  Verify instruction by instruction with a differential fuzz against GPGX's own Z80 core (`z80/z80.c`, same idea as `tools/insnfuzz`).
4. Runtime `tools/z80rt.c` (in the repo: registers, memory callbacks, chip write hooks; no game code) + a build step that compiles the generated driver; run it in lock step with the GPGX Z80 first and compare the chip write trace (`Y` / `P` lines, cycles included) with the golden trace on all recordings.
5. Switch: the Z80 emulation is no longer run (`LANDSTALKER_SND=native`, default after the A/B passes); mailbox writes of the 68K go to the recompiled driver's RAM.
6. Own clock: run the recompiled driver by audio time, not by the emulator's frame; fast forward without the music speed up (issue #11 part 2).

## 6. Status 2026-10-28 (steps 3 and 4 done in SHADOW mode)
- Step 3: `tools/z80recomp.py` + `tools/z80rt.h` + differential fuzz `tools/z80test/run.sh ROM [cases] [seed]` (every instruction of the driver on random state against GPGX's `z80/z80.c`: registers, flags incl. the undocumented bits, cycles, memory writes AND the time stamp of every write to the chip area): 870 800 random cases, 0 differences; a deliberately broken flag is caught at once.
- Step 4: `tools/sndnative.c` + `tools/patch_sndnative.py` (shadow mode, `LANDSTALKER_SND_SHADOW=1`): the recompiled driver runs inside the game next to GPGX's Z80 on the same inputs and every YM2612 write, PSG write and YM status read (value + the chip's timer B counter) is compared live with GPGX's.  Result over 7 of the user's recordings (3 000 - 6 300 frames each, intro, Mercator, island map, dialogue speech blips, sword effects, ending): about 19 million events, 0 mismatches, 0 Z80 RAM differences.  Debug modes: `LANDSTALKER_SND_SHADOW=2` (end of every z80_run: pcs and times), `3` (instruction trace of both from `LANDSTALKER_SND_DBGFROM`), `4..7` (timer / bus wait / frame boundary details).
- What the model needed to be exact (all found by the comparison, each is a GPGX behaviour, not a Z80 one): the instruction's cycles are added BEFORE its memory accesses; GPGX keeps the ROM byte swapped (`cart.rom[a ^ 1]`); every Z80 access to the 68K bus (banked ROM window, `$7F00..`) waits 3 Z80 cycles and, while a VDP DMA runs, until `dma_endCycles`; the chip's sample grid is 1008 master cycles with the frame rebase of `sound_update()` (the new count is the grid point after the frame's end minus the frame length, even when the chip already ran one sample further); the FM timer B / busy flag arithmetic (`sndnative.c`); `gen_zbusreq_w` / `gen_zreset_w` can set the Z80 clock BACK to the 68K's time (after a long DMA wait): `lk_nat_resync`; the boot stub of the system init runs first (the recompiled copy starts at the reset that follows the driver upload, with the registers and RAM GPGX has then).
- The 68K side is untouched (no behaviour change, nothing reaches the chips yet): with the variable off the shadow code is inert.
- Build: `build.sh` runs `z80recomp.py "$ROM" core/z80drv_gen.c` (the generated file is derived from the ROM: never commit it; other ROMs / the CI selftest get a stub) and `patch_sndnative.py`.  `firstrun.py` takes the steps from `build.sh`, so the AppImage path gets it too (not tried).

## 11. Z80 boot stub recompiled (2026-10-31, step 2 of the way off the emulator)
- **What it is:** SEGA's standard Z80 init program (38 bytes at ROM `$0006AE`, uploaded by the 68K init before `InitZ80Driver $0006FA`): `xor a`, LDIR that clears Z80 RAM `$0026..$1FFF`, pops zeros into all registers, `di`, `im 1`, writes `jp (hl)` (`$E9`) to address 0 and parks there. In THIS game it never gets past the LDIR: the 68K takes the bus and uploads the driver after ~229 `z80_run` calls (frames 0..3), the driver start then keeps the registers the interrupted LDIR left.
- **Built:** `tools/z80recomp.py` makes `z80boot_step()` next to `z80drv_step()` in the generated `core/z80drv_gen.c` (found by its standard first 14 bytes in the user's ROM; stub function when absent); new forms `ld sp,hl`, `ldir` (one transfer per step like GPGX), `ld i,a`, `ld r,a`, `im 1`, `ld (hl),n`, `jp (hl)`; the self written `jp (hl)` is executed from memory. `tools/z80rt.h`: field `im`. `tools/sndnative.c` (`LK_Z80BOOT v1`, `lkb_run` / `lkb_check`): when the native driver is not active yet and Z80 RAM holds the stub, `z80_run` runs the recompiled stub instead of GPGX's interpreter; stateless (registers taken from and written back to GPGX's Z80 struct every run). Not modelled: R's per-fetch count, WZ (not observable here).
- **Switch:** default ours (`z80boot: the Z80 boot stub runs recompiled`); `LANDSTALKER_Z80BOOT=gpgx` = interpreter; `=check` = both on the same state, all registers, clock and Z80 RAM compared after each run.
- **Acceptance:** check mode 229 runs, 0 differences; `tools/z80test/run.sh` (repaired: stubs for the later hooks) driver 139 328 cases 0 differing, boot stub 1 601 cases (every instruction, random state, LDIR edge counts) 0 differing, the whole stub from reset to its `jp (hl)` loop identical incl. memory; timebench IDENTICAL on 74 / 74 (vs `LANDSTALKER_Z80BOOT=gpgx` and vs the baseline before this step).
- **GPGX's Z80 interpreter** now runs nothing in normal play (still the fallback for other ROMs and for `LANDSTALKER_SND=gpgx` / shadow tests).
