# TEXT LAYER (languages) - design, 2026-10-26

Goal: Options > Language (English / Deutsch / later more) for the US and EU ROM with ONE ROM per player. Translations are OUR OWN text (shipped in `lang/*.json`, no ROM content);
everything decoded from a ROM (`tools/stringdump.py`, `~/.landstalker_text/`) stays local. Decision history: HANDOFF 0a120-0a121.
Why not the German ROM as a base / text source: its code differs (1169 routines), its Huffman tables and charset are its own (INDEX status 2026-10-26, FORMATS section 5).

## 1. What is replaced
| Source | Where the game reads it | Format (FORMATS section 5) |
|---|---|---|
| dialogue / messages (2175) | `PrintString $022F26` -> `InitCompString $022FCC` (string id in D0) -> Huffman `GetNextChar $023044` | compressed |
| NPC / special names, item names, menu strings (170) | `LoadUncompressedString $02949A` (A2 = entry, D7 = count - 1 afterwards) | count byte + font codes |
| intro captions, credits, save location names | own routines | later |

## 2. Hooks (wrappers via `func_table_register`, like `lk_h_awpt` in `patch_own.py`)
1. **Dialogue**: wrapper of `InitCompString $022FCC`: run the original; if a translation exists for the id: write the translated WORD STREAM into a RAM buffer, set `dword_FF1844` (alternative character source, already used by the game for inserted names: words = glyph codes, control characters = `~handler` words, `$FFFF` ends the stream, codes `$69/$6A/$6B` hyphen / breaking space / break point are handled in `GetNextChar loc_23094`) and point the Huffman source (`dword_FF1848`, set after `InitCompString` by `PrintString`) to a dummy entry `{02, 00}`: bit 0 = the end marker `$55` right after the start context (VERIFIED with `stringdump.decode_string`: 128 of 256 one-byte streams decode to the empty string). So the game never touches the original compressed text. The end of the string is then the normal `$55` of the dummy.
   Hook point detail to settle: `PrintString` calls `InitHuffmanDecomp` and stores A0 into `dword_FF1848` AFTER `InitCompString`, so the dummy pointer must be set by a second wrapper (e.g. `InitHuffmanDecomp $02469C`) or the stream is prepared there.
2. **Names**: wrapper of `LoadUncompressedString`: after the original, redirect A2 to a RAM copy of the translated entry and set D7 (count - 1).
3. **Glyphs**: the printer reads `MainFontPtr $022E84` (long in the ROM image) + 30 bytes per code, also the own renderer (`patch_owntext.py` line 28 `bus_read32(0x022E84)`). German needs ä ö ü ß Ä Ö Ü: new codes `$6C $6D $6E $71 $72 $73 $74` = ä ö ü ß Ä Ö Ü (outside the Huffman range; chosen because their tile slots are BLANK in the menu font, slots `$6F` / `$70` hold other art), glyphs derived from a o u / S with a diaeresis in the free rows above (checked on the font) and a drawn ß; the extended font (original 0..$6B + new) lives in an EXTRA AREA appended to the in-memory ROM image (beyond 2 MB) and `$022E84` is pointed to it (no change on disk). Widths: advance = widest row, automatic.
4. Line breaking: the game wraps itself at x > `$0114` (`sub_22F66`); explicit `{NewLine}` / `{SoftNewLine}` stay where the translation puts them. German is ~15-25 % longer: text box fit is tuned by playing (8 lines per box).

## 3. Language file `lang/<code>.json` (in git, our text only)
```
{"meta": {"code": "de", "name": "Deutsch", "version": 1},
 "strings": {"0004": {"h": "<first 8 hex digits of sha1 of the ENGLISH source>", "t": "Wally: Miss Kayla ist wunderschoen."}, ...},
 "names": {"item:01": {"h": "...", "t": "Zauber{BreakSpace}Schwert"}, ...},
 "ui": {"yesno_no_x": 168, "yesno_cursor_yes_x": 208, "yesno_cursor_no_x": 296}}
```
`ui` = layout values that depend on the word lengths of the language (defaults = the US values, so English needs none): the Yes / No prompt `YesNoPrompt $024724` prints 'Yes' at x `$50` and 'No' at x `$A0` and moves a cursor sprite between FIXED x positions `$D0` / `$120` (`g_VDPSpr02_X`); the German original build uses `$A8` for the second word and `$128` for the cursor (every position that is compared / set in `loc_247E8` / `loc_24804`). Our hook wraps or patches these constants from `ui`; the same mechanism takes later layout values (Use / Equip choice, menu column widths).
Control codes are written as in `stringdump.py` (`{Speaker}`, `{NewLine}`, `{Item}`, `{Number}`, `{ContinuePrompt}` ...) and must appear in the translation as in the English source (checked). `h` makes sure a translation is only used when the ROM's English text is the one it was written for (US and EU are identical, other versions simply fall back to English).

## 4. Build step
`tools/langbuild.py ROM lang/de.json out.bin` (runs in `build.sh` / `firstrun.py` on the player's machine): decodes the ROM's strings, drops translations whose hash does not match, converts the text to word streams / name entries and writes a compact binary (id -> offset) plus the extended font. The game loads it at start (`LANDSTALKER_LANG` / `~/.landstalker_lang`, Options > Language row). English = the original path, bit exact (hooks do nothing).

## 4b. Binary format (DONE, `tools/langbuild.py`)
`'LKLG' u16 version(2) u16 n_str u16 n_name u16 n_ui u16 n_glyph u16 n_text`, then `n_str x {u16 id, u32 blob offset, u16 words}`, `n_name x {u8 table, u8 index, u32 offset, u8 bytes}` (tables: 0 char, 1 special, 2 default, 3 item, 4 menu), `n_ui x {u16 key, u16 value}` (1 yesno_no_x, 2 yesno_cursor_yes_x, 3 yesno_cursor_no_x), `n_glyph x {u8 code, 30 bytes text box glyph, 8 bytes menu font glyph}`, `n_text x {u8 key length, u8 value length, key, value}` (our own UI text, section 8), then the blob (strings as u16 words incl. `$FFFF`, names as bytes). All big endian. Control codes become `~HANDLER[k] & $FFFF` (table `HANDLER` in langbuild = the game's `ControlChars` table). Entries whose English hash or control codes do not match are dropped with a message (US and EU give identical output). Extended glyphs: lower case umlauts = a / o / u + dots in row 2 (free rows above the x height), capitals lose one middle row and get the dots in row 0, sharp s drawn; preview with `--preview out.png` (checked by eye 2026-10-26, user has not judged them yet).

## 6. German grammar with inserted item names (checked 2026-10-26 in the disassembly of the German build, structure only, no text copied)
The German original avoids cases by SENTENCE SHAPE: the item sentences are `{Item} BENUTZT.` / `GEGESSEN.` / `GETRUNKEN.` / `GEFUNDEN.` / `BEKOMMEN.` / `GENOMMEN.` (item name first, past participle after it, so the name stays in the nominative and no article is needed). For the few sentences that need an article it has an ITEM ARTICLE TABLE (`ItemArticles`, one nibble per item = article class, 32 bytes; `GetItemArticle` / `GetItemUseString` / `GetItemFoundString` pick a sentence variant by that class: string id = base + offset[class]). RULES for our translation: (1) write item sentences like the original: name first, participle after it; (2) do NOT write `für den {Item}` style sentences with an article before an inserted name; (3) if a sentence really needs an article, plan a class table + sentence variants like the German build (a hook on the string id selection, not needed yet). My first test line `Hier ist dein Geld für den {Item}.` broke rule 2 on purpose of the test only.

## 7. Menu font (item lists, 2026-10-26)
The Start menu lists (Use / Equip item names) are NOT printed with the text box font: `InitInv_LoadMenuFont $00D9FC` expands the 1bpp 8x8 `MenuFont $00DC76` (160 tile slots, slot = character code) to `g_Buffer + $84 = $FF2C84` and queues one DMA (`QueueDMAOp $000DD6`, a0 = $FF2C84, a1 = 0) to VRAM $0000. The language binary therefore carries an 8 byte menu glyph per extra character (`n_glyph` record = code + 30 bytes text box glyph + 8 bytes menu glyph); `patch_lang.py` wraps `QueueDMAOp` and writes the extra tiles into the RAM buffer just before that DMA. Checked: 'Schlüssel' in the Use list.
OPEN (own UI text): the bar of the file select ('Start / Copy / Delete / Options'), our own Options pages (Video, Audio ... On / Off) and the Start menu bar are drawn by our own C text code in `patch_options.py` with fixed English words; they need the same language lookup (the menu table entries `menu:03..05` exist in the translation).

## 8. Our own UI text (menus drawn by `patch_options.py`, 2026-10-26)
Language file block `ui_text`: `{"Video": "Video", "Quality of Life": "Komfort", "Off": "Aus", ...}` = English word / phrase -> translation, stored as `n_text` entries (umlauts as bytes `$80..$86` = ä ö ü ß Ä Ö Ü, `lk_chr` maps them to the extra glyph codes). The runtime function `lk_lang_tr(english)` returns the translation or the English text itself; it is applied inside the three low level printers (`lk_fs_print` = text engine, `lk_menu_print_nodma` = Start menu bar, `lk_opt_put` = tile words of the Start menu pages) and in `lk_opt_val` (value words), so every label, title, value word, binding name and bar word is translated without touching the callers; strings that are composed (`< Deutsch >`) are not keys and pass through. The two bars are laid out from the measured text widths (`lk_fs_width`: sum of glyph advances - 2; English gives exactly the old positions, other languages: file select bar 0x0C..0x114 with gaps up to 24 px, Start menu bar words centred on 0x33 / 0x89 / 0xE1, the arrow X = text x + $80 follows). A language change redraws the whole page (the window and the Start menu page). Also translated through `lk_lang_tr` (2026-10-26): the on-screen hints (QUICKSAVE / QUICKLOAD / NO QUICKSAVE / NOT NOW / QUICK SAVE OFF - SEE OPTIONS / FAST FORWARD OFF - SEE OPTIONS / FAST FORWARD %dX = format strings are keys; `lk_osd_say` translates its argument; the hint font `lk_glyph` in `display_core.c` is 5x7 capitals only and got Ä Ö Ü ß from the UI bytes), the Quick Equip hint texts and overlay names (SWORD / ARMOUR / BOOTS / RING, MAGIC ... VENUS, starting equipment, the letters `SABR` as a 4 character key), and the item info bar (words Use / Equip / Options at the bar layout positions, ~50 descriptions of at most 34 characters; the cache of rendered bars is flushed when `lk_lang_gen()` changes). NOT translated: the hotkey hints of the display options (FILTER / SCALE / WIDE / FULLSCREEN / COORDINATES / MODEL VIEW / DE-DITHER: keyboard F keys, debug flavour), hidden rows, the Windows / AppImage launcher texts (`firstrun.py`).
