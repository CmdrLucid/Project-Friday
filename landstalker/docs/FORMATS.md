## 2. Room map and blocks
- The map is a 2D array of 16-bit **block indices**, **148 bytes (74 blocks) per row**, foreground at `$FF7C02`, background layer `$2AC8` bytes behind (`$FFA6CA`). Address of a cell: `$FF7C02 + 2*x + 148*y` (`MapPtrAndCellFromXY $00C37E`, row offsets from table `$00C3CE`; `MultiplyD1By148 $C3A0`, `D2By148 $C3AA`). V
- A **block = 16x16 px = 2x2 tiles**. `BlockToTiles $00A748` turns one block into 4 queue entries: plane A row 0, plane B row 0, plane A row 1, plane B row 1; foreground block index from `(a6)`, background index from `$2AC8(a6)`, tile data from `$FF5C02`, VRAM destination words from table `$00A77E` (8 bytes per plane cell, indexed by cell index d2). V
- The map is **isometric**: a screen rectangle is a diamond in map coordinates. Strip loaders `LoadTopTiles $00A61C`, `LoadBottomTiles $00A698`, left `$00A6B0`, `LoadRightTiles $00A730` each queue 12 blocks next to the camera. Map pointer step -146 / +150 bytes, plane cell index step -$1F / +$21; the scroll planes are a 32-cell x 16-cell ring (wrap at `$200`). V (disassembly), loaded set = union of diamonds of radius 11 (PLANEMAP). V
- Room data loading: `WarpToRoom -> LoadRoomParams -> GetTilemap` (clears the height map with `move.l #$40004000,(a1)+`), `LoadRoom $002996`. Room number `$0255` = Massan church (save loads here), `$0250` = Massan village outside. V/I

## 3. VDP interface
- The game draws only through a RAM queue (`$FF3900`) flushed in VBlank by `FlushVdpWriteQueue $002686`: per entry a word (VDP address low part) + `move.w #3,(a1)` (so only VRAM `$C000-$FFFF` = scroll planes/window) + a long (two horizontally adjacent nametable entries), 4 entries per pass, auto-increment 2 (`$8F02`); pointer reset to `$FF3900` afterwards. V
- Sprite attribute table: 320 words uploaded every frame (`UploadSpriteTable $000AE4`); hscroll table 2 words/frame (`UploadHScroll $00126C`); full-screen DMA fills with 40-word rows (`FillScreenByDma $000D22`: 40 columns only). V
- `ClearScrollPlanes $000B38` ran once per 3400-frame session (start), room changes do not call it. V
- (V, 2026-10-10 night) Map screen layout: lines 0-23 = window plane (HUD, reg 18 = $03), lines 24-~183 = planes A/B (map), from ~184 the HInt handler `HandleHBlankInterrupt $001184` switches the display OFF (reg 1 = $8124) and flushes the VDP write queue in that extra blanking (so the queue is flushed in the HInt band, not only in VBlank). Dialogue: `g_HIntLineReg $FF0FC4` = $8AA0 -> HInt at line 160 sets reg 18 = $1C (window plane down to line 224 = text box), display stays on. Evidence: DEBUGGING 'Full-height picture'.
- Screens: the window plane carries the HUD/text box. See DEBUGGING "Widescreen: map-frame detection" for how screens are told apart (heuristic).

## 4. Entities (sprites)
- Player at `$FF5400`: X +0, Y +1, Z word +$12, FallRate +$20, JumpRate +$21, GroundHeight +$22, Action word +$2C (bits 0-3 walk, 4 fall, 5 jump, 8-11 sword, 12 ladder). V
- Other entities: 15 slots of 0x80 bytes from `$FF5480` (two 0x40 halves with identical position fields); slot numbers are reused (`$FF5700` held the chicken, `$FF5980` the dog in the replay). V
- Fields (inferred from disassembly/dumps): `+00/+01` tile X/Y, `+02/+03` sub-tile (steps of 2, `0x0808` at spawn), `+04` bits 7-6 facing, `+08` step size (word & 0xF), `+09/+0A/+0B/+0C` flags/ids from the room data, `+12` height, `+14/+16` centre, `+18/+1A` X extent, `+1C/+1E` Y extent, `+22` ground height (bit 4 disables the collision test), `+28` pointer, `+2A` behaviour id, `+48` bit 6 = collision test off, `+4C` bit 7 = delete. I
- Processing: `UpdateSprites $0178C8` loops over the slots, `SpriteBehaviour_Table $017918` (104 entries x 4 bytes, indexed by `+2A`) jumps to the behaviour; `InitSprites $019514` creates entities from the per-room table `RoomSpriteData $01B932`; `GetSpriteDims $019814`. V/I
- Walking NPC step `NpcMoveStep $017D62`/`$017B50` dispatches by facing to 4 blocks (+Y SW `$17D62` via `$38C`, -X NE `$17E1E` via `$392`, +X SE `$17CAA` via `$386`, -Y NW via `$380`); each moves by +8 and tests the next tile only when crossing a tile boundary: `CheckCollisionX/Y` (stubs `$380/$386/$38C/$392` -> `$31A6/$31FE/$31A0/$31F8`: height-map test, tile `& $6F` vs height `>>4`, carry = blocked), `CheckSpriteCollision` (`$3A4` -> `$2F76`); step is undone when blocked. V (funcdiff vs real core, 20,000 trials)
- NPC walking directions are random (RNG does not come from the VDP HV counter). V

## Map loader: plane cell index d2 (added 2026-10-10, Deck session, measured with LANDSTALKER_BLOCKLOG over the massan walk replay, 1343 blocks)
 * V (2026-10-10): the strip loaders (LoadTopTiles $00A61C, LoadBottomTiles $00A698, LoadLeftTiles $00A6B0, LoadRightTiles $00A730) take the START plane cell `d2` from a table indexed by the word `g_StripStartCellIndex` ($FF1184, x2), NOT from the camera ($FF1124/$FF1125). `MapPtrAndCellFromXY` ($00C37E) only converts (x,y) to the map pointer and leaves d2 unchanged.
 * V: `row = (y + r0) mod 16` (100 % of 816 blocks); the cell index follows `d2 = (x + 0x20*y + K) mod 0x210` (the ring modulus is 0x210: a row wrap moves the column by 16), K differs per room / phase and by +-0x20 through the loader's wrap quirks; values >= 0x200 are folded back by 0x20; max d2 seen $1FF. Index into BlockToTiles_VramDestTable ($00A77E, 8 bytes per cell).
 * V: one BlockToTiles call = 4 queue entries (word VRAM command + long tile data) = 24 bytes in the VDP write queue ($FF3900.., count byte $FF1128 in blocks, write pointer $FF1840); one strip = 12 blocks. The queue has NO overflow check in the game: more than ~288 blocks reach the player struct at $FF5400 (found when the widescreen strip extension queued 24*k extra blocks per call).
 * V (2026-10-10, supersedes the mod-0x210 rule above): the plane cell of a map block relative to another block of the same strip: `row' = (row + dy) mod 16`, `col' = (col + dx + 16 * floor((row + dy) / 16)) mod 32` with d2 = row*32 + col; 0 mismatches in 9773 consecutive block pairs (BLOCKLOG, fuzz seed 3). The mod-0x210 form is wrong in 32.5 % of the cases.

## VDP write queue (added 2026-10-10, Deck session)
 * V: buffer `$FF3900` (`g_VdpQueueBuffer`), write pointer `$FF1840` (long), count `$FF1128` (BYTE, number of 4-entry groups = map blocks; `ADD.B #$0C` per strip loader call, the flush `FlushVdpWriteQueue $002686` decrements it per group). An entry = 6 bytes: word = VRAM command high word (`$40xx..$7Fxx` = VRAM write, the low command word is always `$0003` => VRAM address = `$C000 + (word & $3FFF)`), then a long = two tile words written at address and address+2 (VDP auto-increment 2, the flush sets reg 15 = 2). One `BlockToTiles` call = 4 entries = 24 bytes (plane A row 0, plane B row 0, plane A row 1, plane B row 1). I (inferred): the game never checks for overflow: more than ~288 blocks reach `$FF5400` (player struct).
 * V (2026-10-10): the widescreen extension runs the strip loaders under `lk_no_charge`, moves the entries it appended into a private buffer (pointer and count restored) and writes them to VRAM natively when `FlushVdpWriteQueue` is entered, so the game cannot tell (RAM dumps identical except unused queue bytes and stack bytes below SP).

## Sound driver (Z80 RAM) and the separate volumes (added 2026-10-13, measured with LANDSTALKER_SNDLOG / LANDSTALKER_ZRAMDUMP over the weapon-shop / inn / fight recording)
- V: the Z80 sound driver (disassembly `code/audio/sounddrv.asm`) keeps **14 channel blocks of 32 bytes from Z80 RAM `$1300`**: YM1..YM6 (`$1300..$13A0`), PSG tone 1-3, PSG noise (`$13C0..$1420`), then the 'type 2' effect channels S2_1..S2_3 and S2_noise (`$1440..$14A0`). Byte `+0/+1` = stream pointer, `+3` = 0 while the channel plays, 1 when it is stopped.
- V: music streams live in the banked ROM window (pointer >= `$8000`), effect streams in the driver's own RAM (pointer < `$2000`, e.g. `$176F`, `$189B`). A type-1 effect (`InitChannelDataForSFX`) OVERWRITES the pointer of the music channel it uses; the type-2 effects use their own blocks but take over hardware FM channels 4-6 and the PSG noise channel (the driver skips the music channel while a type-2 block plays).
- V: `pt_SFX` (58 words) is at Z80 `$1594`. The speech blip is a PSG tone-3 effect (frames with `ProcessChar_loc_23104` running = frames with the PSG3 block on an effect pointer); the sound id comes from `$FF1154` (per speaker), the only trap site is `$023132`.
- Implementation (`tools/patch_sndsep.py`): `lk_snd_sfx_mask()` = hardware channels (bit 0-5 FM, 6-8 PSG tone, 9 noise) that play an effect right now; `YM2612Update` scales `out_fm[c]` per channel, `psg_write` scales the written volume. 100 % / 100 % = byte-identical output. Verified: music 0 % / effects 0 % / speech off change only the sound (checkpoint key masks identical in 6000 frames except 2 frames with speech off, which skips one sound queue entry).
- ?: the DAC (hardware FM channel 6 in sample mode) is counted as music unless a type-2 effect block 3 plays; PSG volume changes of a running note are applied at the next volume write of the driver (the driver rewrites volumes every tick).
- Settings: `~/.landstalker_audio` ("music effects speech", percent / percent / 0|1), env `LANDSTALKER_VOL_MUSIC`, `LANDSTALKER_VOL_SFX`, `LANDSTALKER_TALK`.

## Screen projection and ground distance (added 2026-10-13, for the Shadow option, measured in Massan / the Massan roof jump)
- V: `CheckEntityOnScreen $004144` stores the entity's screen position in `+0E` (X) and `+10` (Y) in VDP sprite coordinates (128 = screen 0): X = x - y + $120, Y = (x + y - 2z) / 2 + $E8 - camera, with x / y = `+14` / `+16` (pixels) and z = `+12`. So **one Z unit = one screen pixel upwards**, Z cancels in X. The point is the box centre at the entity's feet.
- V: `GetDistanceToGround $0032C6` (a0 = entity) returns d5 = Z minus the highest floor below the box (height map `ScanHeightMapUnderEntity` and platform-like entities `FindEntitySurfaceBelow`); it caches the floor in byte `+39` (the Shadow option restores it). The floor point under the entity is therefore at screen (X, Y + d5).
- V: the game has its own shadow sprites in `BuildEntitySpriteEntries $00437A` (tiles `$24C4` for the player / `$478C` for others, entity flag `+0C` bit 1 and `+48` & 7); Nigel never has the flag in normal play (checked while jumping), so no shadow shows under him.
- V (GPGX): the final per-line pixel buffer `linebuf[0]` carries priority bits in bit 6 / bit 7 even in normal mode (all three table variants `pixel[0x00|i]`, `[0x40|i]`, `[0x80|i]` hold the same colour), so no bit can be used to mark pixels; the Shadow option keeps its own mask and darkens the converted output pixels in `remap_line`.
