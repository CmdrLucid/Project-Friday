## 2. Room map and blocks
- The map is a 2D array of 16-bit **block indices**, **148 bytes (74 blocks) per row**, foreground at `$FF7C02`, background layer `$2AC8` bytes behind (`$FFA6CA`). Address of a cell: `$FF7C02 + 2*x + 148*y` (`MapPtrAndCellFromXY $00C37E`, row offsets from table `$00C3CE`; `MultiplyD1By148 $C3A0`, `D2By148 $C3AA`). V
- A **block = 16x16 px = 2x2 tiles**. `BlockToTiles $00A748` turns one block into 4 queue entries: plane A row 0, plane B row 0, plane A row 1, plane B row 1; foreground block index from `(a6)`, background index from `$2AC8(a6)`, tile data from `$FF5C02`, VRAM destination words from table `$00A77E` (8 bytes per plane cell, indexed by cell index d2). V
- The map is **isometric**: a screen rectangle is a diamond in map coordinates. Strip loaders `LoadTopTiles $00A61C`, `LoadBottomTiles $00A698`, left `$00A6B0`, `LoadRightTiles $00A730` each queue 12 blocks next to the camera. Map pointer step -146 / +150 bytes, plane cell index step -$1F / +$21; the scroll planes are a 32-cell x 16-cell ring (wrap at `$200`). V (disassembly), loaded set = union of diamonds of radius 11 (PLANEMAP). V
- Room data loading: `WarpToRoom -> LoadRoomParams -> GetTilemap` (clears the height map with `move.l #$40004000,(a1)+`), `LoadRoom $002996`. Room number `$0255` = Massan church (save loads here), `$0250` = Massan village outside. V/I

## 3. VDP interface
- The game draws only through a RAM queue (`$FF3900`) flushed in VBlank by `FlushVdpWriteQueue $002686`: per entry a word (VDP address low part) + `move.w #3,(a1)` (so only VRAM `$C000-$FFFF` = scroll planes/window) + a long (two horizontally adjacent nametable entries), 4 entries per pass, auto-increment 2 (`$8F02`); pointer reset to `$FF3900` afterwards. V
- Sprite attribute table: 320 words uploaded every frame (`UploadSpriteTable $000AE4`); hscroll table 2 words/frame (`UploadHScroll $00126C`); full-screen DMA fills with 40-word rows (`FillScreenByDma $000D22`: 40 columns only). V
- `ClearScrollPlanes $000B38` ran once per 3400-frame session (start), room changes do not call it. V
- (V, 2026-10-10 night) Map screen layout: lines 0-23 = window plane (HUD, reg 18 = $03), lines 24-~183 = planes A/B (map), from ~184 the HInt handler `HandleHBlankInterrupt $001184` switches the display OFF (reg 1 = $8124) and flushes the VDP write queue in that extra blanking (so the queue is flushed in the HInt band, not only in VBlank). Dialogue: `g_HIntLineReg $FF0FC4` = $8AA0 -> HInt at line 160 sets reg 18 = $1C (window plane down to line 224 = text box), display stays on. Evidence: DEBUGGING 'Full-height picture'.
- Screens: the window plane carries the HUD/text box. See DEBUGGING "Widescreen: map-frame detection" for how screens are told apart (heuristic).

- Player at `$FF5400`: X +0, Y +1, Z word +$12, FallRate +$20, JumpRate +$21, GroundHeight +$22, Action word +$2C (bits 0-3 walk, 4 fall, 5 jump, 8-11 sword, 12 ladder). V
- Other entities: 15 slots of 0x80 bytes from `$FF5480` (two 0x40 halves with identical position fields); slot numbers are reused (`$FF5700` held the chicken, `$FF5980` the dog in the replay). V
- Fields (inferred from disassembly/dumps): `+00/+01` tile X/Y, `+02/+03` sub-tile (steps of 2, `0x0808` at spawn), `+04` bits 7-6 facing, `+08` step size (word & 0xF), `+09/+0A/+0B/+0C` flags/ids from the room data, `+12` height, `+14/+16` centre, `+18/+1A` X extent, `+1C/+1E` Y extent, `+22` ground height (bit 4 disables the collision test), `+28` pointer, `+2A` behaviour id, `+48` bit 6 = collision test off, `+4C` bit 7 = delete. - Processing: `UpdateSprites $0178C8` loops over the slots, `SpriteBehaviour_Table $017918` (104 entries x 4 bytes, indexed by `+2A`) jumps to the behaviour; `InitSprites $019514` creates entities from the per-room table `RoomSpriteData $01B932`; `GetSpriteDims $019814`. V/I
- Walking NPC step `NpcMoveStep $017D62`/`$017B50` dispatches by facing to 4 blocks (+Y SW `$17D62` via `$38C`, -X NE `$17E1E` via `$392`, +X SE `$17CAA` via `$386`, -Y NW via `$380`); each moves by +8 and tests the next tile only when crossing a tile boundary: `CheckCollisionX/Y` (stubs `$380/$386/$38C/$392` -> `$31A6/$31FE/$31A0/$31F8`: height-map test, tile `& $6F` vs height `>>4`, carry = blocked), `CheckSpriteCollision` (`$3A4` -> `$2F76`); step is undone when blocked. ## Map loader: plane cell index d2 (added 2026-10-10, Deck session, measured with LANDSTALKER_BLOCKLOG over the massan walk replay, 1343 blocks)
 * V (2026-10-10): the strip loaders (LoadTopTiles $00A61C, LoadBottomTiles $00A698, LoadLeftTiles $00A6B0, LoadRightTiles $00A730) take the START plane cell `d2` from a table indexed by the word `g_StripStartCellIndex` ($FF1184, x2), NOT from the camera ($FF1124/$FF1125). `MapPtrAndCellFromXY` ($00C37E) only converts (x,y) to the map pointer and leaves d2 unchanged.
 * V: `row = (y + r0) mod 16` (100 % of 816 blocks); the cell index follows `d2 = (x + 0x20*y + K) mod 0x210` (the ring modulus is 0x210: a row wrap moves the column by 16), K differs per room / phase and by +-0x20 through the loader's wrap quirks; values >= 0x200 are folded back by 0x20; max d2 seen $1FF. Index into BlockToTiles_VramDestTable ($00A77E, 8 bytes per cell).
 * V: one BlockToTiles call = 4 queue entries (word VRAM command + long tile data) = 24 bytes in the VDP write queue ($FF3900.., count byte $FF1128 in blocks, write pointer $FF1840); one strip = 12 blocks. The queue has NO overflow check in the game: more than ~288 blocks reach the player struct at $FF5400 (found when the widescreen strip extension queued 24*k extra blocks per call).
 * V (2026-10-10, supersedes the mod-0x210 rule above): the plane cell of a map block relative to another block of the same strip: `row' = (row + dy) mod 16`, `col' = (col + dx + 16 * floor((row + dy) / 16)) mod 32` with d2 = row*32 + col; 0 mismatches in 9773 consecutive block pairs (BLOCKLOG, fuzz seed 3). The mod-0x210 form is wrong in 32.5 % of the cases.

## VDP write queue (added 2026-10-10, Deck session)
 * V: buffer `$FF3900` (`g_VdpQueueBuffer`), write pointer `$FF1840` (long), count `$FF1128` (BYTE, number of 4-entry groups = map blocks; `ADD.B #$0C` per strip loader call, the flush `FlushVdpWriteQueue $002686` decrements it per group). An entry = 6 bytes: word = VRAM command high word (`$40xx..$7Fxx` = VRAM write, the low command word is always `$0003` => VRAM address = `$C000 + (word & $3FFF)`), then a long = two tile words written at address and address+2 (VDP auto-increment 2, the flush sets reg 15 = 2). One `BlockToTiles` call = 4 entries = 24 bytes (plane A row 0, plane B row 0, plane A row 1, plane B row 1). I (inferred): the game never checks for overflow: more than ~288 blocks reach `$FF5400` (player struct).
 * V (2026-10-10): the widescreen extension runs the strip loaders under `lk_no_charge`, moves the entries it appended into a private buffer (pointer and count restored) and writes them to VRAM natively when `FlushVdpWriteQueue` is entered, so the game cannot tell (RAM dumps identical except unused queue bytes and stack bytes below SP).

V
- Health values: 6143 = 24 hp (full at the start of the 'Ryuma' save), 2047 = 8 hp, 3071 = 12 hp (after Friday's revive), 0 = dead. V

## Sound driver (Z80 RAM) and the separate volumes (added 2026-10-13, measured with LANDSTALKER_SNDLOG / LANDSTALKER_ZRAMDUMP over the weapon-shop / inn / fight recording)
- V: the Z80 sound driver (disassembly `code/audio/sounddrv.asm`) keeps **14 channel blocks of 32 bytes from Z80 RAM `$1300`**: YM1..YM6 (`$1300..$13A0`), PSG tone 1-3, PSG noise (`$13C0..$1420`), then the 'type 2' effect channels S2_1..S2_3 and S2_noise (`$1440..$14A0`). Byte `+0/+1` = stream pointer, `+3` = 0 while the channel plays, 1 when it is stopped.
- V: music streams live in the banked ROM window (pointer >= `$8000`), effect streams in the driver's own RAM (pointer < `$2000`, e.g. `$176F`, `$189B`). A type-1 effect (`InitChannelDataForSFX`) OVERWRITES the pointer of the music channel it uses; the type-2 effects use their own blocks but take over hardware FM channels 4-6 and the PSG noise channel (the driver skips the music channel while a type-2 block plays).
- V: `pt_SFX` (58 words) is at Z80 `$1594`. The speech blip is a PSG tone-3 effect (frames with `ProcessChar_loc_23104` running = frames with the PSG3 block on an effect pointer); the sound id comes from `$FF1154` (per speaker), the only trap site is `$023132`.
- Implementation (`tools/patch_sndsep.py`): `lk_snd_sfx_mask()` = hardware channels (bit 0-5 FM, 6-8 PSG tone, 9 noise) that play an effect right now; `YM2612Update` scales `out_fm[c]` per channel, `psg_write` scales the written volume. 100 % / 100 % = byte-identical output. Verified: music 0 % / effects 0 % / speech off change only the sound (checkpoint key masks identical in 6000 frames except 2 frames with speech off, which skips one sound queue entry).
- ?: the DAC (hardware FM channel 6 in sample mode) is counted as music unless a type-2 effect block 3 plays; PSG volume changes of a running note are applied at the next volume write of the driver (the driver rewrites volumes every tick).
- Settings: `~/.landstalker_audio` ("music effects speech", percent / percent / 0|1), env `LANDSTALKER_VOL_MUSIC`, `LANDSTALKER_VOL_SFX`, `LANDSTALKER_TALK`.

## Screen projection and ground distance (added 2026-10-13, for the Shadow option, measured in Massan / the Massan roof jump)
- V: `CheckEntityOnScreen $004144` stores the entity's screen position in `+0E` (X) and `+10` (Y) in VDP sprite coordinates (128 = screen 0): X = x - y + $120, Y = (x + y - 2z) / 2 + $E8 - camera, with x / y = `+14` / `+16` (pixels) and z = `+12`. So **one Z unit = one screen pixel upwards**, Z cancels in X. The point is the box centre at the entity's feet.
- V: `GetDistanceToGround $0032C6` (a0 = entity) returns d5 = Z minus the highest floor below the box (height map `ScanHeightMapUnderEntity` and platform-like entities `FindEntitySurfaceBelow`); it caches the floor in byte `+39` (the Shadow option restores it). The floor point under the entity is therefore at screen (X, Y + d5).
- V: the game has its own shadow sprites in `BuildEntitySpriteEntries $00437A` (tiles `$24C4` for the player / `$478C` for others, entity flag `+0C` bit 1 and `+48` & 7); Nigel never has the flag in normal play (checked while jumping), so no shadow shows under him.
- V (GPGX): the final per-line pixel buffer `linebuf[0]` carries priority bits in bit 6 / bit 7 even in normal mode (all three table variants `pixel[0x00|i]`, `[0x40|i]`, `[0x80|i]` hold the same colour), so no bit can be used to mark pixels; the Shadow option keeps its own mask and darkens the converted output pixels in `remap_line`.

## Scroll arrows of the item list (added 2026-10-16, V = seen in the disassembly and in a VRAM dump of the open Start menu)

- V: Equip grid (loop `$00EAD4`): cursor column `$FF2C18` (0..4), row `$FF2C1A` (0..3 = sword, armour, boots, ring); cell item ids = ROM `EquipInventoryLayout $00ECE0`, 5 per row (`BA 01 03 02 04 / BB 09 0A 0B 0C / BC 07 05 06 08 / BD 0F 0D 0E 10`, bit 7 = 'nothing'); owned = `GetItemQtyAndMaxQty $022ED0` d1 >= 0. Use list: item = `$FF2C5C + ((scroll $FF2C06 + row $FF2C0C) * 2 + column $FF2C0A)`. The Use list runs on the stack `GameLoop -> $00774A -> $00D3BE`, the Equip grid under `CheckForMenuOpen $007624`.
- V: text box: tile buffer `$FF3900` (the same RAM as the VDP write queue buffer), 4 bpp, a 16 pixel text line = 8 pixel columns of two tiles (64 bytes), line stride `$900`, text y `$FF1129` (+$10 per line); the DMA to VRAM `$A500` is `QueueDMAOp $0002C6` with the size in WORDS (`$0D80` with the inventory open = 6912 bytes); `DMACopyTextboxTiles $02355A` ends in FlushDMACopyQueue (waits for the next VBlank). Character codes of the game font: `.` `$40`, `,` `$41` (guessed, works), `:` `$47`, `-` `$48`; no `%`, no apostrophe known.
- V: the block map is 74 x 74 words (`$FF7C02`, stride 148, background layer at `+$2AC8`); block addresses outside `$FF7C02..$FFA6C9` read the background layer / other RAM (see DEBUGGING 'Full height: garbage band', brick stub).
- V: platforms: entity `+30` = offset of the entity it stands on (`UpdateSupportingEntities $0024F4`), objects on platforms move through `UpdateLinkedEntity $019114` (borrowing the platform's `+9` / `+2D` for one step) and have no move flags of their own; the player's link is `$FF5430`.

## Sprite upload (added 2026-10-17, dev; V = measured with `tools/spritetrack.py` on per-frame RAM dumps, R = read in the lordmir disassembly)
 * R: VRAM tile slots of sprites are DYNAMIC. Every game pass `LoadSprites $00401C` -> `InitSpriteLoad $004214` restarts the allocator at tile `$03A8`; each entity of the visible list (`g_VisibleEntityList $FF11DE`, words = offset from `Player_X $FF5400`, `$FFFF` ends) gets the next range. The player always takes `$2C` tiles, the others the tile count of their frame (`LoadObjectVDPSprites $00460C`, size table `VDPSpriteTileCount $00467A`). `TileCopySource` (+06 bit 4 of the init flags) lets an entity share another one's tiles. Tile bytes: uncompressed or LZ77 per frame (`LoadSpriteTiles $00473E`, flag `$2000` = compressed), queued as DMA; hard stop at tile `$04F4` (beep + Sleep).
 * V: sprite KEY in the entity struct: `SpriteGraphic` (+0B), `AnimationIndex` (+24, byte offset into the animation table), `AnimationFrame` (+26); first VDP tile = `TileSource` (+06) & `$7FF`. Frame data: `SpriteGfxNNNFrameMM` in the ROM (`sprites/spriteframes`, `$121E1C..`), chosen as `SpriteGfxPtrPtr[gfx] -> animation -> frame`.
 * V (slime replay `slime_idle_overlap` frames 1000..1200, 4 entities): every entity's `TileSource` appears in the RAM mirror of the sprite attribute table (`g_VDPSpr16_Y $FF05D0`, 8 bytes per entry: y, size|link, attr word, x), the player sits at `$3A8..$3D3`. Over 200 frames no tile base changed.
 * V (ship replay `ship_band_garbage` frames 300..4100, 22448 entity-frames): a tile base of the same entity changes ONLY inside room loads / fades / long text boxes (frames where the SAT mirror is not rebuilt: runs such as 346-351, 586-592, 2380-2755, 3073-3385); in steady play 0 changes. The base is NOT a stable key; use (SpriteGraphic, AnimationIndex, AnimationFrame) (+ palette from `GetSpritePalette $1A4468`). While a text box is open the entity list and the SAT mirror disagree, so a state-driven renderer must not trust `TileSource` then.
 * Tool: `python3 tools/spritetrack.py DUMPDIR FRAME...` prints visible entities (slot, type, gfx, anim, frame, tile, flags) and the used SAT entries.

## Entity -> screen projection (added 2026-10-17, dev; R = `CheckEntityOnScreen $004144`, V = checked with the model overlay `tools/patch_model.py` on `slime_idle_overlap` frame 1100, 320 and 352 px wide)
 * a = CentreX (+14) - Z (+12) - cam `$FF1200`; b = CentreY (+16) - Z - cam `$FF1202` (word variables, the camera in sub-tile units).
 * Stored in the entity: +0E = a - b + $120 (VDP sprite x, 128 = screen 0), +10 = ((a + b + k) >> 1) + $E8 (VDP y), k = 0 for the player, else word `$FF1180` ^ 1. Picture pixel: x = +0E - $80 = a - b + $A0, y = +10 - $80 = ((a + b + k) >> 1) + $68. One Z unit = one screen pixel up; one sub-tile step in X moves the picture (+1, +0.5), in Y (-1, +0.5).
 * V: the same formula applied to the box corners (+18 x1, +1A x2, +1C y1, +1E y2) at the entity's Z gives the footprint diamond; it sits exactly under Nigel and under the slime; the model's box centre differs from the stored sprite position by 0..2 px for objects (the box centre is not CentreX), 0 px for the player. Entities off screen keep +0E / +10 = 0 (picture -128).
 * Overlay tool: `LANDSTALKER_MODEL=1` (cross = stored position, diamond = box footprint, label = sprite graphic id / animation / frame), `LANDSTALKER_MODEL_LOG=N` prints the numbers.

## Height map cells (added 2026-10-17, dev; V = grid overlay on `slime_idle_overlap` frame 1100, room 439)
 * V: `g_HeightMap $FFD192` = 74 x 74 WORDS (row stride 148 bytes, size `$2AC8`), cell (x, y) at `$FFD192 + 148 * y + 2 * x`, indexed with the SAME tile coordinates as the entity (Player_X +0 / Player_Y +1): world units x * 16 .. x * 16 + 15 (entity Centre = tile * 16 + sub, e.g. tile 18 sub 8 = 296). The map blocks `g_ForegroundBlocks` / `g_BackgroundBlocks` use the same cell index (`ConvertXYToBlockPtr $00A... = y * 148 + 2 * x`; BG block at +0, FG block at +$2AC8 from the FG pointer, id & $03FF, `BlockToTiles`).
 * V: first byte of the cell word: low nibble = floor height in 16 unit steps (Z = h * 16: Nigel standing on `$01xx` has Z 16), high nibble = type (`$40` + height 0 = void / empty, the room is cleared to `$4000`; `$43`, `$21` = special / wall cells, appear along edges and obstacles); SECOND BYTE = FLOOR TYPE (decoded 2026-10-17, see below).
 * V: projection of a cell corner (wx, wy) at floor height z: a = wx - z - cam `$FF1200`, b = wy - z - cam `$FF1202`, screen x = a - b + $A0, y = ((a + b) >> 1) + $68 (same as entities, section 'Entity -> screen projection'); a cell is a 32 x 16 px diamond.

### Height map cell, both bytes (decoded 2026-10-17, dev; V = per-frame RAM dumps of 7 replays, 38 real rooms, 3814 world frames)
 * V: byte 0 = `bit 6` blocked for everybody (`ScanHeightMapUnderEntity $003302` mask `$40`), `bit 5` blocked for NPCs only (mask `$60` for non-player entities), `bit 4` (raft track, never seen set in these rooms), low nibble = floor height (Z = h * 16). Cell `$4000` = void. `Player_GroundHeight` (+22) = this byte of the cell under the entity (low nibble equal in 3760 / 3814 frames).
 * V: byte 1 = FLOOR TYPE, `Player_GroundType` (+23) = this byte of the cell under the player (equal in 3753 / 3814 frames; the rest are frames at a cell border); `ProcessFloorType $00603C` runs `byte & $3F` through a jump table. In all 38 rooms the byte only takes values `$00..$2E`. Table (index = value): 00 normal, 01 door NE, 02 door SE, 03 door SW, 04 door NW, 05 stairs, 06 door, 07 pit, 08 warp pad, 09 ? (`$006290`), 0A none, 0B ladder NW, 0C ladder NE, 0D ? (`$00629C`), 0E counter, 0F elevator, 10 spikes, 11..14 signs NW 1..4, 15..18 signs NE 1..4, 19 swamp, 1A locked door (no handler here), 1B..21 none, 22..25 signs NE 5..8, 26 locked door SE, 27 locked door SW, 28 Nole staircase, 29 lava, 2A ice NE, 2B ice SE, 2C ice SW, 2D ice NW, 2E Goddess statue. Seen in play data: 00-08, 0B, 0E, 15, 26, 2E; the others come from the jump table only.
 * Check against the picture: in room 439 (forest, `slime_idle_overlap`) the door cells (`$03` door SW, `$06` door) lie exactly on the exits at the bottom of the room, the model view draws a yellow cross there.
 * Warning: while the island map or another full-screen picture is shown the arrays are scratch buffers; only trust a frame while `g_VisibleEntityList` is not empty and the room is a map room (the ROM decoder `tools/romroom.py` gives the real room data at any time).

## Block map: which block is drawn where (added 2026-10-17, dev; V = `tools/blockfind.py` on 299 dump frames of 7 replays + screenshot check of the model view mode 'blocks')
 * V: the two arrays `g_ForegroundBlocks $FF7C02` (layer A, plane A) and `g_BackgroundBlocks $FFA6CA` (layer B, plane B) are indexed like the height map (`148 * y + 2 * x`, block id = word & `$03FF`, tiles = `g_Blockset $FF5C02 + 8 * id`: 4 tile words, top row then bottom row), but the picture is ISOMETRIC: block (x, y) sits in the plane at TILE (8 px) column `2 (x - y) + K1`, tile row `x + y + K2` (a brick pattern of 2 x 2 tile blocks, neighbours never overlap; the earlier 16 px cell form `((x - y + k1), ((x + y + k2) >> 1))` is only right for cells with x + y even, which is why odd cells seemed to disagree) (checked on the real visible blocks of room 439: col - (x - y) = 24..26, row - (x + y) / 2 = 1..2 over 45 unique blocks; the plain rectangle `col = x, row = y` and three sheared variants fit worse by a factor 5..20). The scroll registers are full-screen (VDP reg 11 = 0), the shear is in the data.
 * V: screen pixel of the top-left corner of block (x, y), layer B / BG array: `sx = 16 * (x - y) + (cam2 - cam0 + 160)`, `sy = 8 * (x + y) - (cam0 + cam2) / 2 + 104` with cam0 = word `$FF1200`, cam2 = word `$FF1202` (the same camera as the entity projection); layer A / FG array: `sx` another 16 px to the left. Measured as the difference between the fitted plane position and this prediction over 299 plane / array pairs: exactly (0, 0) for layer B in 18 cases, (-16, 0) for layer A in 37, the rest within a few pixels / 8 px vertical steps (the plane rows are 16 px, the odd diagonal sits 8 px off). The model view mode 'blocks' draws these squares + the BG ids (hex): the squares follow the seams of the picture (dirt path blocks `034`, `0DE`, grass `047` / `023` form vertical stacks).
 * Consequence: a block is NOT the graphic of the height map cell under it; each cell (x, y) owns the 16 x 16 piece at the position above, pieces of neighbouring cells overlap the diamonds. Note the older entry (strip loaders step map (+1, -1) <-> plane cell (+1, -1)) describes the loading order only.
 * Open: the 8 px parity cases; the exact stacking of the two layers (plane A over plane B, priority bits in the tile words, see below).

### Block word flags (bits 10..15) and tile word flags (checked 2026-10-17, dev; V = 35 real rooms from the replay dumps, R = disassembly)
 * V: the block word has NO flags: the id is the whole low 10 bits (`$0000..$03FF`, the blockset `g_Blockset $FF5C02` holds exactly 1024 entries of 8 bytes up to `g_ForegroundBlocks $FF7C02`), `BlockToTiles $00A748` masks `$03FF` and ignores bits 10..15. In 35 real rooms (both layers, about 130 000 cells) bits 10..15 are never set; the only occurrence is a junk filler in room 178 (layer A, 1216 cells of `$86BC`, x 0..73, y 2..19, nowhere near the room's height map x 18..39, y 19..31, so never drawn). While the island map screen is shown the code reuses these arrays as scratch buffers (`DisplayIslandMap` writes at `g_ForegroundBlocks + $17E`), so frames of that screen do not hold the room; rooms 494 / 495 / 497 / 543 themselves are normal map rooms (they decode exactly from the ROM, see 'Room map data in the ROM').
 * V: flips, palette and priority are in the TILE words of the blockset (VDP name table format): bit 15 priority, bits 14..13 palette line, bit 12 vertical flip, bit 11 horizontal flip, bits 10..0 tile index. Counts over the tiles of all blocks used in the 40 rooms (4 words per block): plain 22348, h-flip 4431, v-flip 1298, both flips 597, palette 1 / 2 / 3 about 1900 / 1100 / 100, priority set 5600 (3063 priority alone, 1821 with h-flip, 705 with both flips ...). So the game builds occlusion (tree tops over Nigel, walls over sprites) with the VDP priority bit of the tile words, and mirrors block artwork with the tile flip bits: an own renderer must apply flip, palette and priority per TILE, not per block.
 * R: map data in ROM (`GetTilemap $002BC8`): a header of 4 signed bytes (left offset, top offset, width - 1, height - 1) followed by the layers; `ExtractMap $002C4A` copies a layer into a cleared 74 x 74 array at that offset (the same offset for height map and blocks, which is why all arrays share the index). Not verified byte by byte.


## Room map data in the ROM (added 2026-10-17, dev; V = `tools/romroom.py`, own Python port of `DecompressMap1 $00CDAE`, compared with RAM dumps of 39 rooms)
 * V: room table: long at `$0A0A00` (= `$0A0A12`, label `RoomDataPtr`) points to 8-byte entries per room number: map data pointer (long, e.g. room 439 -> `$0BB49B`), tileset, palette, height limits, music (`LoadRoomParams $002B4E`).
 * V: map data = ONE bit stream (MSB first) followed by a byte aligned part. Header (8 bit each): left offset, top offset, width - 1 (cells), then a count X with rows per layer = ((X + 1) >> 1); two layers of w x rows words follow (FG then BG), 10 + 10 bit counters (a5 base, a4 start), eight 12 bit offsets (table), then stage 1 = `gamma coded skip` (k zero bits, a 1, k bits: skip = 2^k + value words), a prefix code for the mark (-1 literal mode, 2 / 4 / stride / stride + 2 / 2 * stride / 2 * table[3 bit] = 'copy from that many bytes back', optional diagonal repeat), stage 2 resolves marks (copy words, or literals: `new id from counter a4 / a5` or a coded reference below the counters), stage 3 = byte aligned RLE of the height map (width, height, then word + run length bytes with 255 continuation).
 * V: placement: FG and BG layer cell (x, y) of the stream goes to RAM array cell (x + left, y + top); the HEIGHT MAP always lands at offset (12, 12) (cell (x, y) of the stream = RAM cell (x + 12, y + 12)). The decoder `romroom.py` reproduces the RAM arrays EXACTLY (all 5476 cells of FG, BG and every non-void height cell) in 35 of 39 rooms; the other four differ only in the game's own changes (rooms 139 / 142 / 632: the top row y = 0 stays empty in RAM although the stream has data there - ExtractMap quirk; room 454: scripted block changes, 22 cells).
 * Use: `python3 tools/romroom.py ROM ROOM [DUMP.bin]` (compare with a RAM dump), `import romroom; romroom.arrays(romroom.decode(rom, room))` gives {'FG','BG','HM'} -> {(x, y): word}. With it any room can be read without running the game (own renderer, room viewer, modding).

## Room graphics in the ROM and drawing a room without the game (added 2026-10-17, dev; V = `tools/romgfx.py`, `tools/romrender.py`, compared with the VDP planes of RAM dumps)
 * V: tile graphics: `TilesetPtrTable $044010` holds a long pointing to a table of pointers (index = entry byte 4 & `$1F`); each points to LZ77 data (`DecompressLZ77Gfx $004AB2`): flag byte, MSB first, 1 = literal byte, 0 = match (byte b1, byte b2: offset = (b1 >> 4) << 8 | b2, length = 18 - (b1 & 15), offset 0 ends). Result 4 bits per pixel (high nibble = left pixel), 32 bytes per 8 x 8 tile, loaded to VRAM tile 0 (room 439: 29952 bytes = 936 tiles). 355 of those bytes differ in a running game (animated tiles overwrite parts).
 * V: block definitions: `BlocksetsGroupsTablePointer $1AF800` -> table indexed by the WHOLE entry byte 4 -> pointer to a list [primary blockset, secondary 0, 1, ...] (secondary index = entry byte 7 >> 5). `DecompBigTiles $00D09C` (own port `romgfx.bigtiles`): 16 bit block count N (4 N tile words), then three run length passes that build the per-word flags (alternating runs: bit 15 priority; skip / or runs: bit 12 vertical flip, bit 11 horizontal flip), then the tile indices through a 16 entry move-to-front ring (new literal = 11 bits and the ring head moves back, or 4 bit reference), the second tile of a pair may be 'previous +- 1' (minus when the first has the h-flip bit). Run lengths are 2^k - 1 + k bits. Primary blocks come first, the secondary list continues (room 439: 343 + 681 = 1024). ALL 1024 blocks of room 439 equal the RAM blockset bit for bit (palette bits included).
 * V: palette: `RoomPals $11C926`, 26 bytes (13 colours, MD format 0BBB0GGG0RRR0) per palette number (entry byte 5) = colours 2..14 of palette line 0; colour 1 is `$0CCC`, colours 0 and 15 are 0 (`SetRoomPal $002D64`). The dump CRAM is GPGX's 9 bit format (B << 6 | G << 3 | R). Lines 1..3 hold sprite / HUD colours; the placed blocks of the rooms checked (439, 700, 632) only use line 0, other rooms may need them (not examined).
 * V: composing a room (`romrender.py`): block (x, y) of the BG array = 2 x 2 tiles at tile column `2 (x - y) + 148`, tile row `x + y`; FG array two tile columns further left (`+ 146`); pixel order high priority A, high priority B, low A, low B (index 0 transparent), sprites not drawn; tile flip bits mirror the tile. Compared with the VDP planes of RAM dumps (index equality over every loaded pixel of the 320 x 224 window, offset search of a few pixels around the camera prediction `origin = (1184 - (cam2 - cam0 + 160), (cam0 + cam2) / 2 - 104)`): after a wider offset search 34 of 39 rooms are >= 99 % (rooms 456, 632, 635 were 41..50 % only because the offset was outside the first search window: 100 % at offsets (-2, 0), (-2, -1), (-2, -1)); three rooms stay lower: 494 (90 %), 644 (90 %), 543 (65 %), all ship / island screens whose water is probably animated or scrolled (not examined); the other small differences are animated tiles and stale ring strips of the VDP. Pixel exact crops: room 439 right corner of the fir group 7200 of 7200.
 * Tool use: `python3 tools/romrender.py ROM ROOM out.png` draws the whole room (room 439: 672 x 384 px, 0.6 s), with a dump as 4th argument it also writes `out_vdp.png` and prints the agreement. `python3 tools/romgfx.py ROM ROOM` prints tile / block counts.
